Part 1: What each print_pgtbl entry contains

Permission bits: V (0x1) valid, R (0x2) readable, W (0x4) writable, X (0x8) executable, U (0x10) user-accessible, A (0x40) accessed, D (0x80) dirty.

va 0x0, perm 0x5B (V R X U A): the first text (code) page. The user can read and execute it but not write it. A is set because the CPU has fetched instructions from it.
va 0x1000, perm 0x1B (V R X U): more text. It has the same permissions, but nothing has touched it yet, so A is not set.
va 0x2000, perm 0x17 (V R W U): the data page holding global variables. It is readable and writable by the user but not executable.
va 0x3000, perm 0x07 (V R W, no U): the guard page. Because the U bit is off, any user access faults, which catches a stack overflow.
va 0x4000, perm 0xD7 (V R W U A D): the user stack. It has been read and written, so both A and D are set.
va 0x5000 to 0x9000, perm 0: unmapped. The heap has not grown yet.
va 0x3FFFFFD000, perm 0x13 (V R U): the usyscall page I added in part 4. It is read-only for the user. Before part 4 this entry was 0.
va 0x3FFFFFE000, perm 0xC7 (V R W A D, no U): the trapframe, which saves user registers on a trap. It is kernel-only because U is off.
va 0x3FFFFFF000, perm 0x4B (V R X A, no U): the trampoline, the code that runs on trap entry and exit. It is executable but the user cannot access it directly.

The physical addresses are not consecutive because xv6 takes free pages from a free list in whatever order they come.

Part 2: What the vmprint leaves are and how they relate to part 1

The leaves in my vmprint output match the entries above:

The two RXU leaves are the text pages (0x5B and 0x1B).
The RWU leaves are the data page (0x17) and the stack (0xD7).
The RW leaf with no U at 0x3000 is the guard page. R and W are set, but without U user code faults on it.
At the top of the address space, the RU leaf is the usyscall page, the RW leaf without U is the trapframe, and the RX leaf without U is the trampoline.

R allows loads, W allows stores, X allows instruction fetch, and U allows access from user mode. Anything not allowed causes a page fault. Interior entries have none of R, W or X set, which means they point to the next-level page table rather than to memory.

Part 4: Which other syscalls could use the shared page

Syscalls that only return information the kernel already holds, with no side effects, can be answered by reading a read-only shared page, so no kernel crossing is needed. Examples are uptime (the kernel updates the tick count in the shared page on each timer interrupt and user code reads it) and getppid (store the parent's PID in the page and update it when the process is reparented). Syscalls that change state or need privilege checks, such as write, fork and sbrk, cannot be done this way.

Part 5: Superpages

My solution uses 95 superpage PTEs (level-1 leaf entries) in the kernel page table. Each superpage covers 2MB, which is 512 pages of 4KB, so each one replaces 512 bottom-level PTEs. In total that saves 95 × 512 = 48,640 bottom-level PTEs. It also saves 95 page-table pages of 4KB each, about 380KB of memory.
